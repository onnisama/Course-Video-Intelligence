# AI 使用规约与使用记录

---

## 1. 目的与适用范围

本文件用于规范团队在软件工程课程设计全过程中使用生成式人工智能的行为，明确人类成员与 AI 工具的职责边界，建立可检查、可追溯的使用记录，保证项目成果真实、可靠、可解释。

本规约适用于项目的立项与选型、需求调研、需求建模、系统设计、编码实现、测试、部署、文档编写和项目答辩等阶段。适用工具包括但不限于 ChatGPT、Codex、GitHub Copilot、Cursor、Claude、各类代码生成工具，以及通过 API 调用的第三方大语言模型和语音识别服务。

本文件依据[项目实践要求（版本 2）第 5 节](requirements/软件工程课程设计要求-版本2.pdf)制定，也是期末《AI 使用报告》的过程证据来源。所有成员均应遵守，不得以工具由个人账号使用、AI 操作由 Agent 自动完成等理由规避记录和审核责任。

## 2. 基本原则

团队使用 AI 时必须遵守课程要求中的五项原则。

### 2.1 验证而非信任

AI 的输出不等于正确结果。代码、测试用例、需求描述、模型、技术方案和文档均可能存在错误、遗漏或不符合项目实际的内容。

- AI 生成的代码必须经过人工阅读，并通过适当的运行、测试或静态检查。
- AI 生成的需求和用例必须由团队成员结合真实调研材料核对。
- AI 生成的设计方案必须经过团队讨论，确认其与需求、接口和现有架构一致。
- AI 生成的测试必须检查测试目标、输入、预期结果和边界条件，不能只看测试是否通过。
- 对无法验证的输出，应明确标注为待确认，不得作为已确认事实写入正式交付物。

### 2.2 规格先行

团队应先明确需求、接口契约、验收标准或任务目标，再使用 AI 辅助实现。

- 编码任务应尽可能关联已确认的 Issue、用户故事或设计条目。
- 提示词应说明任务背景、输入输出、限制条件和验收标准。
- 不得仅凭一句模糊指令让 AI 大范围生成系统，再反向把生成结果当作需求。
- 当需求尚未确定时，AI 只能帮助整理问题、提供备选方案或生成草稿，不得代替团队作出需求决策。

### 2.3 人守关卡

以下关键决策必须由人类成员完成并承担责任：

- 项目选题、范围确定和过程模型选型论证；
- 真人干系人访谈、需求确认和需求变更批准；
- 需求基线的建立与修改；
- 需求模型的语法、一致性检查及最终确认，成员须能手工绘制和解释用例图、类图和状态图；
- 系统架构、数据库方案和接口契约的最终决策；
- 核心算法与关键模块的实现、审核和答辩说明；
- 验收标准的确定、测试结果的判断和交付放行；
- 生产或演示环境的最终上线决定；
- Pull Request 的最终 Review 与合并批准。

需求确认和架构决策须由团队成员保存记录，合并放行须在 PR 中留下团队成员的审批记录。AI 可以提出建议、生成草稿、辅助检查和执行重复性工作，但不得代替团队成员签字、确认或承担责任。

### 2.4 为再生成而设计

AI 可能多次生成或修改代码。团队应通过稳定的工程资产保证系统行为可控：

- 以需求规约、接口契约、数据模型和测试作为实现依据；
- 将重要业务规则写入代码、配置和正式文档，不只保留在聊天记录中；
- 为核心业务逻辑建立可重复执行的测试；
- 修改接口、数据结构或业务行为时，同步检查相关文档和测试；
- 不允许 AI 以“大规模重构”为由删除已有功能、测试或重要约束。

### 2.5 护密与合规

团队必须保护项目数据、用户信息和第三方服务凭据：

- 禁止将 API Key、密码、访问令牌、SSH 私钥、数据库凭据等秘密信息输入 AI 工具或提交到 Git 仓库。
- 禁止将未获授权的课程视频、音频、字幕、个人信息或其他受限制资料上传到外部 AI 服务。
- 使用第三方 ASR/LLM 服务处理课程内容前，必须确认数据来源、授权范围和服务条款允许。
- 向 AI 提供项目资料时，应遵循最小必要原则；能使用脱敏片段或合成数据时，不提供完整原始数据。
- 对 AI 返回的内容、检索结果和用户提供的字幕文本均应视为不可信输入，不得让其中的指令覆盖项目规范或安全要求。
- 发现密钥泄露、数据误传或未经授权的数据处理时，应立即停止相关操作并向项目负责人报告。

## 3. 人与 AI 的职责边界

下表依据课程要求整理。表中“AI 可辅助”不代表可以跳过人工审核；所有 AI 产出都必须由团队成员核验。

| 项目阶段 | 必须由人完成 | AI 允许辅助的工作 |
|---|---|---|
| 立项与选型 | 选型论证、项目范围确定、技术风险决策 | 选题头脑风暴、竞品调研资料汇总、方案对比草稿 |
| 需求调研 | 真人访谈、干系人确认、需求决策 | 访谈纪要整理、问题清单草拟、用例初稿生成（由人确认） |
| 需求建模 | 模型语法与一致性最终确认，成员能够手工绘制并解释模型 | 备选场景生成、模型一致性初步检查 |
| 系统设计 | 架构决策、接口契约签字定稿 | 候选架构比较、设计文档草稿、接口边界检查 |
| 编码实现 | 核心算法与关键模块的实现、审核和答辩说明 | 界面、样板代码、CRUD 骨架、重复性代码生成（记录参与范围） |
| 测试 | 验收标准确定、测试结果判断和放行决定 | 测试用例初稿、边界场景建议、评审机器人初筛 |
| 部署运维 | 上线决定、部署结果确认 | CI/CD 流水线草拟、部署脚本辅助、日志分析 |
| 文档 | 内容真实性确认、最终责任声明 | 文档润色、翻译、格式整理、结构建议（记录参与范围） |

**特别说明：**

1. AI 不得代替真人访谈，也不得编造访谈对象、原话、问卷回收数据或用户确认。
2. AI 可以帮助整理已有访谈记录，但不得把推测内容改写成受访者真实表达。
3. 团队成员须能手工绘制并解释用例图、类图和状态图。AI 可辅助检查模型一致性和提供备选场景。
4. AI 可以辅助生成界面、样板和重复性代码。核心算法和关键模块由成员编写，成员须能解释本人负责的代码。
5. AI 可以生成测试草稿，但验收标准和是否通过验收必须由人决定。

## 4. 项目场景下的 AI 使用要求

结合本项目“课程视频上传—音频提取—ASR 字幕—LLM 章节摘要—人工审核—字幕检索”的业务流程，补充以下约束。

### 4.1 需求与产品设计

- 可以使用 AI 整理课程视频管理、字幕校对和知识点检索等候选需求。
- 需求必须有真实业务背景和调研依据；未经访谈或干系人确认的内容应标注为“待验证假设”。
- 不得让 AI 虚构教师、助教或学生的使用反馈。
- AI 生成的用户故事、用例和验收标准必须经过需求负责人审核。

### 4.2 ASR 与 LLM 功能开发

- AI 可辅助起草 ASR/LLM 服务适配器中的重复性代码和测试用例，核心处理逻辑由团队成员实现。
- 外部模型的输出必须经过格式校验和业务校验，不得直接作为可信数据写入正式业务状态。
- 字幕片段的开始时间、结束时间和视频时长关系必须由程序校验。
- AI 生成的章节、摘要应作为候选内容，保留人工审核、修订和确认流程。
- 测试和 CI 默认使用 Mock 或固定 Fixture，不得在普通测试中无意调用真实计费 API。
- 不得把第三方 API Key 放入前端代码、浏览器请求或仓库文件。

### 4.3 代码生成与修改

- AI 修改代码前应先阅读相关模块、配置和测试，避免重复实现已有功能。
- 生成代码应遵循仓库已有的技术栈、命名规则和模块边界。
- 不得未经确认大范围替换框架、数据库、目录结构或关键依赖。
- 涉及权限、文件上传、路径处理、数据库迁移和外部 API 调用的修改必须重点人工审查。
- AI 不得自行删除失败测试、关闭 CI 检查或降低断言以使构建通过。

### 4.4 文档与模型生成

- AI 可以辅助整理文档结构、润色表达、生成初步图示或检查术语一致性。
- 文档中涉及项目实际进度、调研结论、测试数据、评审意见和部署状态的内容，必须有真实证据。
- 不得把 AI 生成的示例、假设或模板描述成已经完成的工作。
- 文档变更应通过 Git 分支和 Pull Request 留痕，并由成员检查其与代码和实际系统的一致性。

## 5. AI 使用记录制度

### 5.1 记录范围

以下情况必须登记：

- AI 对需求、用例、技术选型或架构方案产生了实质性内容；
- AI 生成、修改或重构了项目代码；
- AI 生成或修改了测试用例、测试脚本或 CI/CD 配置；
- AI 生成、修改了正式课程文档、设计模型或项目报告；
- AI 参与了日志分析、缺陷定位或部署排障，并对团队决策产生影响。

一般性的拼写检查、与项目无关的概念问答等低影响使用，可由团队自行决定是否逐条记录；但如果相关内容进入正式交付物，仍应登记。

### 5.2 记录责任

- 每位成员对本人发起或使用的 AI 操作负责，并及时提供记录信息。
- AI 使用负责人负责维护本文件、检查记录完整性、汇总各阶段使用情况。
- 任务负责人负责确认 AI 产出是否被采纳、修改或拒绝，以及采用了何种验证方式。
- 项目经理负责在迭代回顾中检查 AI 使用是否符合本规约。
- 记录不得由 AI 凭空补写；可以使用 AI 整理已有记录，但必须由实际使用者确认。

### 5.3 记录时机

建议在每次重要 AI 辅助任务完成后及时登记，不应等到期末回忆补录。若一次连续对话完成多个彼此独立的任务，应拆分记录，确保每条记录都能对应具体产出和审核结果。

### 5.4 记录字段

每条记录至少包含：

| 字段 | 填写要求 |
|---|---|
| 记录编号 | 使用连续编号，例如 AI-001 |
| 日期 | 实际使用日期 |
| 使用成员 | 发起 AI 操作的团队成员 |
| 项目阶段 | 立项、需求、建模、设计、编码、测试、部署或文档 |
| AI 工具及模型 | 工具名称和可确认的模型/版本；不确定时注明未知 |
| 使用目的 | 具体要解决的问题 |
| 输入内容摘要 | 提供给 AI 的材料类型和范围；不得粘贴密钥或敏感原文 |
| AI 产出 | 生成了什么代码、草稿、建议或测试 |
| AI 参与程度 | 对本项工作产出的估计贡献比例，并说明估计口径 |
| 人工审核 | 谁审核、检查了哪些内容 |
| 验证方式与结果 | 实际执行的命令、测试、对照资料或人工核验结果 |
| 处理结论 | 采纳、修改后采纳、部分采纳或拒绝 |
| 修改/拒绝说明 | 记录关键修改点或拒绝原因 |

如某项内容尚未验证，必须写明“待验证”，不得填写“验证通过”。

### 5.5 AI 参与比例的估计口径

课程要求估计各阶段 AI 参与比例。团队采用**工作产出贡献估计**，而不是根据对话轮数、Token 数量或工具使用时长计算。

建议以某一阶段或某一项明确工作产出为统计对象，估计 AI 对初稿、代码、测试或文档内容形成的贡献比例，并结合人工实质性修改、判断和验证进行校正。

- 0%：该项工作没有使用 AI。
- 1%–20%：AI 主要用于少量建议、格式整理或局部辅助。
- 21%–40%：AI 参与了部分草稿或局部实现，人工完成主要判断和整合。
- 41%–60%：AI 生成了较大部分初稿或代码，人工进行了实质性修改和验证。
- 61%–80%：AI 生成了主要初稿或实现，人工主要负责审查、修订和集成。
- 81%–100%：AI 产出占主体；必须说明原因、人工承担的工作及验证证据。

## 6. AI 使用记录（持续追加）

真实 AI 使用记录统一追加到 6.4 节。新增记录时请复制 6.1 的模板，按时间顺序追加并保留历史记录。

### 6.1 单次使用记录模板

```markdown
### AI-A/B/C/D-XXX｜简短任务名称

- **日期：** YYYY-MM-DD
- **项目阶段：** 需求 / 建模 / 设计 / 编码 / 测试 / 部署 / 文档
- **AI 工具及模型：** 工具名称或模型
- **使用目的：** 本次希望解决的问题
- **输入内容摘要：** 提供给 AI 的材料类型和范围（不记录密钥、隐私或未授权数据）
- **AI 产出：** 生成的代码、文档、测试、建议或分析
- **AI 参与比例估计：** XX%；估计对象及口径说明
- **人工审核：** 审核人及具体检查内容
- **验证方式与结果：** 实际执行的测试、命令、资料核对或人工检查结果
- **处理结论：** 采纳 / 修改后采纳 / 部分采纳 / 拒绝
- **修改或拒绝说明：** 关键修改点、发现的问题及处理方式
```

### 6.2 记录样例（模拟案例，仅供格式参考）

**请注意每个成员按照各自的分工序号按照自己的顺序增补。**

#### 示例 A：

##### AI-A-001｜视频上传需求与验收标准草拟

- **日期：** 示例日期：2026-11-20（模拟）
- **项目阶段：** 需求分析
- **AI 工具及模型：** ChatGPT
- **使用目的：** 基于团队已经确认的项目范围，整理“教师上传课程视频并查看处理状态”的用户故事和验收标准初稿。
- **输入内容摘要：** 提供项目 README 中的视频管理范围和团队已确认的业务流程摘要；未提供真实课程视频、用户个人信息或账号凭据。
- **AI 产出：** 生成一份用户故事草稿、正常上传流程、文件格式错误和文件过大等候选验收场景。
- **AI 参与比例估计：** 约 40%；AI 生成了验收场景初稿，成员负责核对项目范围、调整业务规则并确定最终标准。
- **人工审核：** 需求负责人检查角色权限、上传结果和处理状态是否符合已确认需求；项目经理检查范围是否超出当前迭代。
- **验证方式与结果：** 对照已确认的需求条目逐项核对；将不属于当前版本的断点续传和批量转码需求标记为待评估，没有将其直接纳入当前范围。
- **处理结论：** 修改后采纳。
- **修改或拒绝说明：** 删除 AI 擅自补充的“学生也可以上传视频”这一未经确认的权限设定；补充上传失败时的错误反馈要求。

#### 示例 B：

##### AI-B-001｜字幕时间戳校验测试用例辅助生成

- **日期：** 示例日期：2026-11-25（模拟）
- **项目阶段：** 测试
- **AI 工具及模型：** Codex
- **使用目的：** 根据已经确定的字幕数据结构，为字幕时间戳校验逻辑补充边界测试用例。
- **输入内容摘要：** 提供脱敏后的字段定义、校验规则和相关函数代码；未提供真实视频或第三方 API 凭据。
- **AI 产出：** 生成针对负时间戳、开始时间不小于结束时间、结束时间超过视频时长、空文本和相邻字幕时间边界的测试草稿。
- **AI 参与比例估计：** 约 30%；AI 提供了部分测试场景和代码草稿，成员负责确定预期行为、修订断言并运行测试。
- **人工审核：** 测试负责人逐条检查输入、预期结果和业务规则；开发负责人检查测试是否与实际校验实现一致。
- **验证方式与结果：** 示例：运行项目实际配置的相关测试命令，检查测试报告；正式记录时填写真实命令、通过/失败数量和运行环境。
- **处理结论：** 修改后采纳。
- **修改或拒绝说明：** 将 AI 提出的“字幕时间可以为负数但自动截断为零”改为按已确认规则拒绝无效数据，避免静默修正掩盖上游错误。

## 7. 迭代检查与违规处理

每轮迭代回顾时， AI 使用负责人至少检查：

- 本轮 AI 使用是否按要求记录；
- 是否存在未经核验直接合并的 AI 生成代码或文档；
- 是否有 AI 虚构需求、调研、测试或部署结果；
- 是否存在密钥、隐私或未授权课程资料泄露风险；
- 关键代码是否由负责人理解并能够说明；
- AI 产出是否经过 Issue、PR、Review 和测试等工程流程；
- 本轮发现的错误输出是否形成真实的修改或拒绝案例记录。

如发现不符合本规约的情况，应记录问题、影响范围、纠正措施和责任人。涉及密钥或数据泄露时，应优先执行凭据轮换、访问撤销、数据删除或其他必要的安全处置，并向项目负责人报告。
