# 项目实施与协作说明

课程硬性要求以[项目实践要求](requirements/软件工程课程设计要求-版本2.pdf)和本班正式通知为准。下文的功能和交付计划用于团队筹备，具体范围由选题审核和后续需求基线确定。

## 课程要求与项目落实

### 规模与约束

| 课程要求 | 项目落实方式 |
|---|---|
| 真实业务背景、中等规模项目，选题须经教师审核 | 面向高校课程视频管理、复习与内容定位场景，使用选题 Issue 留存审核结论 |
| 至少 3 个可交付增量 | 按基础平台、AI 结构化处理、智能检索与交付分阶段实现 |
| 至少 20 个用例 | 在需求分析阶段建立用例清单，包含功能和非功能需求用例 |
| 至少 2 个非功能需求用例 | 重点考虑权限安全、异步处理响应性、外部服务故障恢复等 |
| 至少 15 个分析类 | 基于业务职责进行 CRC 分析和类建模，不以数据库表数量替代分析类 |
| 至少 3 种用户角色 | 教师、助教、学生；管理员作为平台管理角色按需纳入 |
| 权限控制 | 后端对课程、视频、字幕和审核操作执行服务端权限校验 |
| 至少 1 个外部集成点，从第三方登录、支付、地图或消息推送中任选其一 | 拟接入 ASR 和 LLM；课程合规方案待确认，详见下节 |
| 至少识别并管理 1 个技术风险 | 重点跟踪 ASR 时间戳质量、AI 输出准确性、视频处理资源和外部 API 可用性 |

### 课程交付清单

按课程进度维护交付物，提交状态以实际验收为准。每周安排见[课堂检查点](checkpoints.md)。

| 交付物 | 验收要点 |
|---|---|
| 项目章程与过程模型论证 | 在 README 中记录章程，团队结合项目特点完成过程模型的选型论证 |
| 需求调研与规约 | 开展真实干系人访谈，形成访谈纪要、SRS、需求基线和变更记录 |
| 需求建模 | 用例图、至少 3 个细化用例及活动图、CRC 卡、类图、至少 2 个关键类状态图 |
| 设计规约与正式评审记录 | 记录体系结构、部署图、数据库、接口和至少 2 个核心构件的详细设计。每份规约保留至少一次正式评审记录 |
| 代码仓库、CI 配置与评审记录 | 全周期 Git 管理，保留 PR 评审和可追溯提交 |
| 迭代开发 | 至少 2 轮计划—构造—测试—评审，并形成迭代计划与回顾 |
| 测试 | 提交单元、集成和验收测试计划与报告，声明核心模块的单元测试覆盖率。由客户视角的成员编写验收用例 |
| 交付演示 | 提供可运行的部署系统与演示脚本，现场各演示至少 1 项功能和非功能特性 |
| AI 使用报告 | 提交 2–3 页报告，记录工具、各阶段参与比例估计、人工把关及 1–2 个真实案例，附团队反思 |
| 组内贡献度互评表 | 按人统计 Git 提交并提交组内贡献度互评表（0–10 分） |

## 外部集成

项目计划集成第三方 ASR 和 LLM 服务，这是核心业务流程的一部分。

任何第三方服务的接入都必须遵守服务条款、数据授权和个人信息保护要求。

## 仓库目录约定

建议目录如下。实施以仓库现状和团队确认的架构为准，按实际需要建立目录，沿用已有模块边界。前后端、API、数据库和媒体处理的具体约定见[工程实现规范](engineering-guidelines.md)。

```text
.
├── .github/              # Issue / PR 模板、GitHub Actions
├── api/                  # API 契约（如采用 OpenAPI）
├── backend/              # 后端业务服务
├── frontend/             # Vue 前端
├── database/             # 数据库初始化、迁移和测试数据
├── docs/                 # 软件工程课程交付文档与模型
├── tests/                # 跨模块测试或端到端测试（按实际项目结构调整）
├── scripts/              # 开发、检查和部署脚本
├── .env.example          # 环境变量名称与示例，不包含真实密钥
├── .gitignore
├── AGENTS.md             # AI 编程助手的项目约束
└── README.md             # 项目说明与团队信息
```

### 文档管理约定

- `README.md` 和 `AGENTS.md` 位于仓库根目录。
- `docs/` 统一存放课程要求的项目文档、需求规约、分析模型、设计规约、测试报告和迭代回顾。
- 文档随仓库进行版本管理，修改通过分支和 PR 提交。
- 只在相应课程阶段创建和维护文档，不提前创建大量空白模板。
- 每张模型图的源文件独立入库，单独提交一个 PR，并与对应的需求和设计保持一致。

## 开发与协作规范

### Issue 与任务管理

- 每项需求及其变更都必须创建 GitHub Issue。缺陷和普通技术任务也通过 Issue 跟踪。
- Issue 正文说明背景、目标、范围和验收标准，负责人使用 `Assignees`，优先级记录在看板的 `Priority` 字段。
- 需求变更须走申请、评审、批准流程并留痕。记录变更原因、影响分析和批准结论，关联实施 PR 后关闭 Issue。
- 重要决策应在 Issue、PR 或版本化文档中留痕。

Issue 标题使用 `[英文类型] 中文描述` 格式。类型按以下写法保留大小写，右方括号后留一个空格。中文描述写清任务对象和目标，技术名词可保留原文。

- `[Project Proposal]` 项目选题，例如 `[Project Proposal] 提交课程视频检索平台选题方案`
- `[Feature]` 功能开发，例如 `[Feature] 支持按关键词检索课程字幕`
- `[Bug]` 缺陷修复，例如 `[Bug] 修复字幕搜索结果跳转时间偏移`
- `[Task]` 普通任务，例如 `[Task] 整理项目文档入口`
- `[Change Request]` 需求变更，例如 `[Change Request] 调整助教的章节审核权限`

### 标签

每个 Issue 选一个 `type:` 标签描述任务类型，再按主要改动选择 `area:` 标签。跨模块时可补充相关 `area:` 标签。

- `[Project Proposal]` 使用 `type: docs` 和 `area: init`。
- `[Feature]` 使用 `type: feature`，`[Bug]` 使用 `type: bug`，`[Change Request]` 使用 `type: change-request`。
- `[Task]` 按内容选 `type: task`、`type: docs`、`type: design` 或 `type: test`。
- `area:` 用于按模块分工和筛选。例如字幕检索用 `area: retrieval`，音视频提取用 `area: video-processing`，调用 ASR 或 LLM 接口用 `area: ai-integration`。

示例 `[Feature] 支持按关键词检索课程字幕` 使用 `type: feature`、`area: retrieval`，排入交付计划后关联 `v0.3 - Intelligent Retrieval`。

### Projects 看板

在 [Course Project Management](https://github.com/users/onnisama/projects/2) 跟踪正在推进或待排期的仓库 Issue，核对每项任务的负责人、标签和所属增量。

- `Status` 表示当前状态。`Backlog` 为待排期或待开始，`In Progress` 为正在处理，`In Review` 为已提交评审或验收，`Done` 为已验收或依流程结案。看板已启用关闭 Issue 的自动化，更新状态前先核对验收或结案依据。
- `Priority` 记录排期优先级。`P0` 用于阻塞当前交付或核心流程的事项，`P1` 用于当前计划内的事项，`P2` 用于可延期的改进。排期调整时同步更新该字段。
- `Milestone` 表示目标交付增量。立项、课堂调研等尚未归入版本交付的事项可留空，按[课堂检查点](checkpoints.md)跟踪。

### Git 分支与提交

- `main` 为稳定分支，开启分支保护并通过 PR 合并变更。
- 功能、缺陷和文档修改均通过独立分支和 PR 完成。

分支名建议使用英文类型和以连字符连接的小写英文短名，例如 `feature/transcript-search`。分支类型按改动内容选择。

- `feature/short-description`
- `fix/short-description`
- `docs/short-description`
- `test/short-description`
- `chore/short-description`

Commit 首行建议采用 Conventional Commits 格式 `type(scope): 中文描述`。类型和可选的模块名使用英文，中文描述写明本次提交实际完成的改动。

- `feat(video): 新增课程视频上传接口`
- `fix(auth): 修复课程资源访问校验`
- `docs(readme): 补充项目文档入口`
- `test(transcript): 补充字幕时间戳边界测试`

### Pull Request

- PR 标题沿用 Issue 的 `[英文类型] 中文描述` 格式，按 PR 实际提交的改动拟定，例如 `[Feature] 实现字幕关键词检索与时间戳跳转` 或 `[Task] 完善项目仓库协作规范`。
- 每个 PR 应聚焦一个 Issue 或一组紧密相关的改动。正文应说明变更目的、主要改动、关联 Issue、实际运行的测试命令与结果、风险和 AI 参与情况。
- PR 至少由一名非作者团队成员评审后方可合并。
- 不得通过无意义拆分提交或 PR 数量制造虚假贡献。

### 质量保障

- 每项核心功能应有明确验收标准。
- 新增或修改业务逻辑时同步增加或更新测试。
- 配置 GitHub Actions 在 push 时自动运行单元测试，合并前以 CI 通过为门禁。
- 测试失败时不得以跳过测试或屏蔽检查的方式绕过质量门禁。
- 按交付计划通过 Actions 自动部署可运行系统，并为每个增量保留 Release 和部署证据。
- 需求、设计、实现和测试之间应保持可追溯关系。

## 安全与数据合规

1. 第三方 API Key、数据库密码、SSH 私钥等只能通过本地环境变量或受控密钥配置提供，严禁提交到 Git。
2. 前端不得直接持有第三方 ASR/LLM API Key；外部 API 调用由后端完成。
3. 仅使用自制、公开授权或已获得明确许可的课程视频和音频进行开发、测试与演示。
4. 未经授权，不得将课程视频、字幕或个人信息发送给第三方 AI 服务。
5. 后端必须校验用户对课程、视频、字幕和审核操作的访问权限，不能只依赖前端隐藏按钮。
6. 上传文件应校验类型、大小和文件名；不得信任客户端传入的文件路径。
7. 日志应避免记录密钥、完整个人信息和不必要的原始媒体内容。
